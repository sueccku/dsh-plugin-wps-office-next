## 1. 一句话结论

1. **场景可达**：干净环境里，模型用 WPS 走完整条链路（模板另存 → 逐个打开 6 家 → 清洗 → 写 216 行 → 两张汇总表 → 柱形图 → PDF），
   **28 项硬判据零红**，其中最关键的三条不变量全部成立：**7 个输入文件 sha256 一个都没变**、
   **216 个单据号不重不漏**、**合计 = 683,576.49（不是"数量×单价"重算的 767,555.97）**。
2. **模型自述与实测逐条一致**：6 家笔数/合计、7 个科目的笔数/金额/占比、10 页 PDF 的构成，都与独立核验对得上；
   它还主动说明了"金额列没重算""占比加总 100%""图表数据源压在 F/G 两列"。
3. **查出 1 个 P2 缺陷并已修**：sheet 名字不存在时，桥把裸 COM `Invalid index (DISP_E_BADINDEX)` 丢给模型；
   现在回的是「工作簿『X』里没有工作表『Y』；这本工作簿现有工作表：…」+ 可执行的下一步。
   回归 `test/excel-sheet-resolve.test.mjs` 15 项，**在修复前的宿主上 7/15 红**。
4. **C7（多工作簿目标歧义）本轮第一次被真实压到，结果是正向的**：7 个工作簿同时打开时，桥按设计发出
   "检测到 N 个打开的工作簿…建议显式指定 sheet"的 `warnings`，模型全程显式点名工作簿/工作表，
   **没有一次写错文件**（A1 全绿是最硬的证据）。
5. **两条"不是缺陷"的记录**（见 §4.2/§4.3）：隐藏工具 `wps_excel_freeze_panes` 被直接调用 → `unknown tool`（一次硬失败+一次重试，
   属广告面决策）；`export_chart_as_image` 失败的真因是**目标目录不存在**，工具提示指对了方向，模型建目录后 4 次导出全部成功。
6. **两条方法学/资产缺陷**：attempt 1 因**测试装置泄漏**（详见 §2.3）判无效；核验器自身对 `datetime` 日期有**一处误判**（已修，见 §4.4）。

## 4. 发现

### 4.1 已修 · P2：sheet 名字不存在时，模型拿到的是裸 COM `Invalid index`

两轮真机各实测一次，形状完全相同：打开《华南-广州分公司_费用明细_9月.xlsx》（表名 `Sheet1`）后，
用 `read_range { sheet: "费用明细" }` 去读（那是别家工作簿里的表名）。

| | 结果 |
| --- | --- |
| 修复前 | `读取数据出错: Invalid index. (异常来自 HRESULT:0x8002000B (DISP_E_BADINDEX))（动作：getRangeData）下一步：确认操作对象存在、名称或序号正确，并且 WPS 处于可操作状态后重试。` |
| 修复后 | `读取数据出错: 工作簿『工作簿2』里没有工作表『费用明细』；这本工作簿现有工作表：Sheet1、Data。（动作：getRangeData）下一步：用 wps_excel_get_sheet_list 或 wps_excel_get_open_workbooks 确认工作簿与工作表名字（多工作簿时先确认操作的是哪一本）` |

- **根因**：`Get-WorksheetByParam` / `Resolve-Worksheet` 把字符串直接交给 `$wb.Sheets.Item($name)`；
  `Format-WpsErrorText` 也没有 `Invalid index` 分支，于是套上通用建议——在多工作簿场景里帮不上忙。
- **修法**：新增 `Get-WorksheetByNameOrIndex`（先按名字 `OrdinalIgnoreCase` / 1 基序号自查，命中返回原对象，
  查不到才抛中文错误并列出该工作簿现有表；列不出时退回原行为）；错误文案加两条分支。
- **顺带收益**：`sheet: "2"` 以前也会 `Invalid index`，现在按序号解析，与既有契约一致。
- **回归**：`test/excel-sheet-resolve.test.mjs`（15 项）—— 修复后 **15/15 绿**；
  用 `tools/make_prefix_host.py` 造一份"修复前宿主"（两处调用还原 + 去掉新增文案分支），同一文件 **7/15 红**。
- 台账：[FIXES 111](../FIXES.md)。

### 4.2 已处置（D4 / R14）· 隐藏工具被直接调用 → `unknown tool` → 提到广告面

这一轮它从"多绕一步"变成**一次硬失败 + 一次重试**。错误文本由 DSH 的 MCP 客户端产生，桥改不了。

**用户已拍板（D4 = R14，2026-10-11）：高频隐藏工具进广告面。** 处置与依据：

- **取证**：把 S1（2 轮）+ S4（2 轮）+ S6（2 轮）共六轮真机轨迹里经 `wps_call` / `wps_batch` 触达的隐藏工具排序

### 4.3 记录（未改代码）· 图表导出失败的真因是"目录不存在"

`export_chart_as_image { outputPath: "D:\s6-run\_check\chart1.png" }` 第一次 `E_FAIL`，工具的下一步提示
就是"确认 outputPath 的目录存在且可写"。轨迹显示模型**先建目录再重试**，后 4 次导出全部成功，
并 `read_image` 目视复核图表，收尾自己删掉 `_check`。这是「提示 → 照着做 → 成功」的正向读数，不是缺陷。

### 4.4 核验器自身缺陷（1 处，已修）

attempt 2 首判 **27/28**，唯一红是 B9：模型把 `发生日期` 写成了**真日期型单元格**（`datetime` + 数字格式
`yyyy-mm-dd`），用户看到的就是 `2026-09-01` —— 完全符合要求，但判据当时用 `str(cell.value)` 比对文本，
把 `datetime` 渲染成 `2026-09-01 00:00:00` 判了红。**这是一次对模型的误判**（与 S3 报告里记过的
"核验器对模型的假指控"同类）。已改成：文本 `2026-09-DD` **或** 真日期型 + 只显示日期的格式都算合规，
带时间部分的格式才算不合规；改完 known-good 仍全绿、各 broken 集行为不变，attempt 2 复判 **28/28**。

### 4.5 方法学：真机走查的"答案库隔离"

见 §2.3。要点：**运行根目录不能和答案库在同一棵树里**。本轮之后，S6 的 fixture/真值/核验器/自检集
分居三处（`test/.artifacts/scenario-s6/`（生成器）、`%TEMP%\s6-grading\`（真值+核验器+自检集）、`D:\s6-run\`（运行）），
并把"会话里是否出现判分资产"变成可机检的门禁（§2.4）。
