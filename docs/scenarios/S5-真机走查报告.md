## 1. 一句话结论

1. **场景可达**：两轮 attempt 都在 3.5–4.6 分钟内产出**全部 4 类交付物**（合订版 1 份 / 每人 docx 24 份 /
   每人 PDF 24 份 / 清单 1 份），**24 项硬判据两轮都是 0 红**，包括最要命的三条：
   两个「王磊」是两份不同文件、暂缓者不产出、缺基数者基数格真的留空。
2. **走查查出 2 个插件缺陷**（都不是模型的问题）：
   - **P0 · 邮件合并整条链路是假的**（`wps_word_mail_merge`）：字段从不落到占位符、正文会被字段码顶掉、
     合并结果里数据落错位置，工具却回 `success` —— 而唯一的测试只断言"产生了新文档"，所以一直是绿的。**已修**；
   - **P1 · `fileNameField` 指向一个不参与替换的列时被无视**（第 1 轮模型自己报上来的）：文件全叫 `row1.docx…row24.docx`。
     **已修**，并顺带支持 `{列名}` 文件名模板。
3. **两轮自述与实测一致**：模型的最终回答里报的份数、缺基数的人、缺部门的人、模板未改动，逐条与独立核验对上；
   两轮都**主动说明**了自己做的判断（基数留空的歧义、姓名里的空格要不要删、文本金额 `¥9,800.00` 的数值化）。
4. **一条方法学发现**：第 1 轮模型为了拿准字段做了两件"没人要求"的事 —— 复制输入 xlsx 后**直接解包 XML**
   核对空格与单元格类型、发现 `fileNameField` 失效后用 CSV 里的「文件名」列**自己改名**。这是无人值守场景里
   真实出现的"AI 绕过工具自己想办法"，值得记进工具设计：**工具要么够用，要么把它绕路的成本显性化**。
5. 静态门禁全绿：`lint` / `verify --static`（19 项）/ `spec-reproduction`（16 项）/ `param-contract` /
   `test:static`（13/13）/ `verify:package`（11 项）/ `gen-numbers --check`（20 项）。
   `test/word-longtail.test.mjs` **48 项全绿**（断言从 3 项扩到 48 项，且**在修复前会红**）。

## 4. 走查查出的缺陷（两个，都已修）

### 4.1 P0：邮件合并整条链路是假的（`wps_word_mail_merge`）

**现象**（裸 COM 插桩探针，可重跑）：

| 观测 | 读数 |
| --- | --- |
| `Fields.Add` 之后母版正文变成什么 | 正文被字段码顶掉：只剩 `«Dept»`（7 字符），模板原文全丢 |
| 占位符是否被替换 | **从不**：合并结果里 `工号：⟨工号⟩` 原样保留 |
| 数据落在哪 | 字段值堆在**上一条记录的末尾**（`2026年10月12日` 之后紧跟 `制造中心（一车间）王磊`） |
| 记录数 | 3 条数据产出 **4 份**内容；`FirstRecord=1,LastRecord=1` 拿到的是**空**记录 |
| 工具自述 | **回 success**（"已按数据源合并到一个新文档（原文档未改动）"） |

也就是说：README 头号卖点「拿一张 CSV 表，一次生成几十份文档，母版不动」**实际没有替换任何数据、还破坏了母版正文**，
而唯一的测试（`test/word-longtail.test.mjs` 的 3 条断言）只查工具自述里的"新文档/字段"四个字，所以一直绿。

**修法**：`MailMerge.Fields.Add` + `Execute()` → **按占位符做 Find/Replace + 逐行渲染**；
新增 `splitDir`（每行一份直接落盘）与 `outputPath`（合订版存盘）；找不到占位符/有字段没替换成功时走
`Add-WpsWarning`（R11 会把 `success` 翻成 `false`），不再静默产出"看起来成功、其实没数据"的文档。

**修复后桥路径验收**：`splitDir` 一次写出 **24/24 份**；抽 5 份（含两个王磊、缺部门、缺基数）逐字段正确；
合订版 24 块 / 23 分页符 / 顺序 == 名单顺序 / 落款 24 次；母版 sha256 未变。

### 4.2 P1：`fileNameField` 指向"不参与替换的列"时被无视

**现象**：`fileNameField: "文件名"`（列里放的是拼好的 `通知书_部门_姓名_工号`）→ 文件全叫 `row1.docx…row24.docx`。

**根因**：`$values` 是按 **`fields`** 建的，不是按 CSV 表头建的；`fileNameField` 指的列只要不在 `fields` 里，
查表永远取空串 → 回落 `rowN` 兜底。（诊断输出见场景卡 §12.5。）

**修法**：`$rowValue` 按**表头**建全列映射；`fileNameField` 顺带支持 `{列名}` 模板。
**验收**：列名形式（`工号` / `文件名`）与模板形式（`通知书_{部门}_{姓名}_{工号}`）三条路径都产出正确文件名。

### 4.3 两个缺陷为什么以前没人发现

1. 邮件合并的测试只断言**工具自述文本**，没有读**落盘的文件** —— 读写同源，一起错；
2. 场景 S1–S4 全是"一份产出"，**没有任何场景压过"N 份产出的完整性"**；S4 把邮件合并显式排除给 S5，
   而 S5 到这一轮才做；
3. `splitDir` / `fileNameField` 是这一轮**新加的能力**，加的时候没有"列不在 fields 里"的用例。

## 8. 已知不可判项（与场景卡 §8 一致）

- 「手工 70 分钟」是场景设定，不是断言。
