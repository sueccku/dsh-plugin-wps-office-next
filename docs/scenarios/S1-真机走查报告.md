## 0. 结论摘要

1. **场景达成**：插件在一条完整真实任务链上做完了全部 7 步要求——另存副本、清理脏数据、6 门店汇总、
   品类汇总、柱形图、页面设置、导出 PDF；**35 项硬判据全过**，`D3=127` 行、`D7=140,459.95`、
   `D8=2,257`、每店金额/销量/折扣单数/占比全部与真值一致，原文件 sha256 未变。
2. **发现 1 个 P0 级插件缺陷**：`wps_excel_remove_duplicates` **省略 `columns` 时只按第 1 列去重**，
   把 131 行塌成 62 行，**却回报「删除行数: 0 / 剩余行数: 132」**（`success: true`）。
   代码位置 `mcp/scripts/wps-com.ps1:2629`，与工具自身文档「不填则根据**所有列**判断」直接矛盾。
   已用**不经模型**的控制变量 A/B 复现（§4.1）。
3. **本轮交付的产物是干净的**：模型自己撞上了这个缺陷、识别出来、**关闭不保存回退**，
   改用「整行 key + COUNTIF 定位 → 精确删行」重做，所以最终文件没有数据损失。
4. **两次执行中断与插件无关**，已定性到模型侧：模型流式输出的工具参数 JSON 写坏
   （一次 `"showLegend":: true`，一次 `batch.calls[]` 里 `"tool"` 键跑到 `args` 外面），
   harness 把整个回合判为 `MALFORMED_RESPONSE` 终止。
5. **缺陷已修并锁死（D4=A）**：桥的默认列与计数都改对了，新增 13 项"读回真值"的回归
   （该回归在修复前的桥上是 4/11），真机整轮 **1270 通过 / 0 失败 / 50 文件**全绿，门禁全过。

## 1. 方法：先证明"核验认得出对错"，再看插件

项目最贵的教训是「假成功 / 静默丢失」类缺陷静态门禁一个都抓不到，而**验证脚本写错会让整场测试失去意义**。
所以顺序是：

1. `tools/make_fixture.py` 独立生成脏数据 fixture（openpyxl 直写，**不经过插件**），同时落真值 `expected.json`；
2. `tools/verify.py` 从 fixture **重新解析**一份真值，与 `expected.json` 对账（不一致 → 先修基建）；
3. `tools/make_known_good.py` 造两份对照产物：
   **known-good**（完全按场景要求做好）与 **broken**（注入 4 类典型缺陷：文本金额、2 条重复行、无图表、无页面设置）；
4. 只有当 **known-good 全绿且 broken 在对应项变红**时，才让模型真机跑场景。

自检确实拦下了问题——**7 处基建缺陷**（全部在我的验证器/fixture 里，不是插件的）：

| # | 缺陷 | 症状 | 修法 |
| --- | --- | --- | --- |
| 1 | 去重键用了「合并单元格的原始 B 列」 | 不同门店的同数据行被误判重复：127 → 126，`湖畔店`/`老街店` 整体丢失 | 键改用**补齐后的门店值** |
| 2 | `print_title_rows` 归一化 | openpyxl 读回 `$1:$1`，判据只认 `1:1` | 比较前去掉 `$` |
| 3 | 图表 XML 命名空间 | openpyxl 写 `<barChart>`、WPS 写 `<c:barChart>`，只认后者会漏判 | 正则允许可选前缀 |
| 4 | **fixture** 块长度重复累加 | `r += item[1]` 与逐行 `r += 1` 双算 → 合并区落错行，`merge_cells` 把门店名清掉 | 块标记不再推进 `r` |
| 5 | 验证器遇未知门店键直接崩 | `KeyError: ''` → 没有结论（比判红更糟） | 未知值单独记账；另加顶层 `E0` 崩溃兜底 |
| 6 | 占比判据只认"存百分数" | 产物存 `0.1573` + `0.00%` 格式（Excel 惯用），界面显示 15.73%，被误判失败 | 两种写法都收，原始值照记 |
| 7 | `fitToWidth` 判据过严 | OOXML 里 `fitToWidth` **省略即默认 1**；WPS 就是省略写法，被误判失败 | 接受 1 或省略，`note` 写明依据 |

> 第 6/7 条是在**看到真产物之后**才改的。改的依据是原始证据（单元格数字格式 `/ 原始 XML`），
> 不是"为了变绿"——详见 §4.2 的 XML 原文。

**当前自检状态**（可重跑）：known-good **35/35 硬检查全过，exit 0**；broken **9 项硬检查变红，exit 1**。

## 4. 发现

### 4.1 P0：`remove_duplicates` 省略 `columns` 时只按第 1 列去重，且回报数字与实际不符

**契约**（`mcp/src/tools/excel/data.ts:341`）：
> `columns`: 用于判断重复的列，如 `["A", "B"]`。**不填则根据所有列判断**

**实现**（`mcp/scripts/wps-com.ps1:2629`）：
```powershell
if ($cols.Count -eq 0) { $cols = @(1) }   # ← 不填 → 只按第 1 列
```

**复现**（不经过模型：`tools/mcp-repro.mjs` 直接对本仓库 `mcp/dist/index.js` 发 `tools/call`；
行数用 openpyxl 读回，不看插件自述）：

| 副本 | 调用参数 | 保存后数据行 | 工具当次回报 |
| --- | --- | --- | --- |
| 原始 fixture | — | 131 | — |
| 未取消合并 + 省略 columns | `A2:G135, hasHeader` | 131 | **失败** `HRESULT:0x8FE30C0D`（如实报错） |
| 未取消合并 + 显式 7 列 | 同上 | 131 | **失败** 同上（如实报错） |
| **取消合并 + 省略 columns** | `A2:G133, hasHeader` | **62** | **"删除重复行完成！原始行数: 132 / 删除行数: 0 / 剩余行数: 132"** |
| 取消合并 + 显式 7 列 | 同上 | 128 | 删除 3 行 |

- **62 = 表里不同日期的个数**，即 131 行被"每天只留一行"地塌掉 → 与模型当年的观察完全一致
  （它记录的是"声称删除 0 行，实际只按第一列去重，把明细删坏了"）。
- 回报 `删除行数: 0 / 剩余行数: 132` 与实际（删了 69 行）不符：`$range.Rows.Count` 在
  `RemoveDuplicates` 之后读到的仍是旧值。**这是"success: true + 数字不对"的假成功**，
  正好落在项目最危险的类别（静默错 > 崩溃 > 挂起）。
- 显式列那条路是**正常**的：它在这个副本上删 3 行 = 2 组真重复 + 1 组**跨门店巧合相同**
  （行 27 城东店 / 行 64 老街店：7 列原样相同，只因门店列是合并单元格、块内为空）。
  → 也就是说：**先填门店列、再去重**才是对的顺序；模型最终产物就是这么做的，127 行全部核对通过。

**最小复现命令**
```powershell
$node = "$env:USERPROFILE\.dsh\dsh-runtimes\dsh-primary-runtime\dependencies\node\bin\node.exe"
Copy-Item test\.artifacts\scenario-s1\input\2026年9月门店销售.xlsx test\.artifacts\scenario-s1\repro\r.xlsx -Force
& $node test\.artifacts\scenario-s1\tools\mcp-repro.mjs default-unmerged "D:\dsh\a\test\.artifacts\scenario-s1\repro\r.xlsx"
```

**影响面**：任何"去掉重复行"的自然请求都可能踩到——用户不会写 `columns`。
**建议（待拍板）**：默认取「区域内全部列」；回报改用调用前后独立取数（或删后重新 `Range()`），
并在读不到真值时回 `warnings` 而不是照旧回 0。

> ⚠️ 这条缺陷**尚未**写进 `docs/FIXES.md` / `baseline/known-defects.md`。是否入库、编号怎么给，
> 会牵动 HANDOFF §5 的 FIXES 编号与 `gen-numbers` 对账，**留给用户拍板**（见 §6 D4）。

**修复（D4=A：修桥 + 补测试，2026-10-10 已实施）**

| 项 | 内容 |
| --- | --- |
| 桥（唯一真源） | `mcp/scripts/wps-com.ps1`：默认列改为 `@(1..$totalCols)`；行数改用新增的 `Get-NonEmptyRowCount`（读 `Value2` 逐行判非空；读不到就回 `$null` + warning，**不再拿地址行数冒充**）；显式列号做范围校验并明确报错；字母列号按"相对区域"换算 |

### 4.2 插件表现正确、但值得记录的地方

| 观察 | 证据 | 评价 |
| --- | --- | --- |
| 合并单元格范围内调用 `RemoveDuplicates` → `0x8FE30C0D` | §4.1 前两行 | 插件**如实报失败**，没有假成功；属 WPS 侧限制 |
| `create_chart` 拒绝非连续区域 | `数据范围格式无效，应为类似 A1:C10 的格式，当前传入: A1:A7,D1:D7` | 校验清晰；模型据此改用辅助区，行为合理 |
| 直呼隐藏工具 → `unknown tool` | attempt 1 有 3 次 `wps_excel_evaluate_formula` 失败，改用 `wps_call` 后成功 | 与 HANDOFF §8 的历史摩擦同源，属"广告面 vs 注册面"的既有设计代价 |
| `wps_help` 被调 **37 次** | 本次 161 次调用的 23% | 工具发现成本很高，值得作为广告面重平衡的输入 |
| 页面设置写的是 WPS 省略式 | `<pageSetup paperSize="9" fitToHeight="0" orientation="landscape"/>` + `<pageSetUpPr fitToPage="1"/>` | `fitToWidth` 省略 = OOXML 默认 1，"一页宽"成立 |

### 4.3 本场景真实需要、但**不在 84 个广告工具**里的能力

本次 36 个 distinct `wps_*` 工具中，**11 个在隐藏面**（必须靠 `wps_help` 发现 + `wps_call` 调用）：

| 工具 | 调用次数 | 在场景里的用途 |
| --- | --- | --- |
| `wps_excel_copy_range` | 16 | 取值/搬运 |
| `wps_excel_set_sheet_appearance` | 16 | 表格外观（导出 PDF 前后） |
| `wps_excel_evaluate_formula` | 14 | **算完核对**（SUM / COUNTBLANK） |
| `wps_excel_set_column_width` | 10 | 列宽 |
| `wps_excel_unmerge_cells` | 9 | 取消合并（用户第 1 条诉求） |
| `wps_excel_delete_rows` | 8 | 删重复行/垃圾行 |
