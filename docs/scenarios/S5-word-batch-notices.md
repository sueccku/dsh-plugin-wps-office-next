## 1. 一句话场景

**宁川精工机械（约 400 人的制造企业）的人事专员周敏**，每次组织架构调整后要做一批**入职通知 / 调薪通知**：
名单是招聘专员发来的 Excel《2026年10月人事通知书名单.xlsx》，正文用公司统一模板《人事通知书_模板.docx》，
每人一份、文件名要能直接当邮件附件名，**缺基数的几个人还要单独标注"发无金额版"，不能编一个数上去**。

现在她的做法是：把模板**另存二十几遍**、对着名单一行一行改姓名/工号/部门/岗位/基数/生效日期、
再逐份导出 PDF、手工改名，**约 70 分钟，每批一次**；
最典型的翻车是**改漏一行**（有人收到别人的通知书）和**把两个同名的人合并成一份**。

> 8. 把打开着的 Word 文档和 Excel 工作簿都存好关掉，然后告诉我现在还开着什么。

## 4. 现在手工怎么做（痛点）

1. 打开模板 → 另存为第 1 个人的名字 → 改 6 个字段 → 导出 PDF → 改名；
2. 重复 24 遍（**跳过暂缓的那 1 个**，这一步每次都要回去确认行号）；
3. 缺基数的 2 个人，把基数那格留空、在备注里写一句说明；
4. 两个"王磊"要特别小心，否则会做成同一份；
5. 全部做完再逐个数文件个数，对一遍名单；
6. 最后关文档、关表格、发邮件。

**耗时约 70 分钟；每批一次；最典型的返工是"有人收到了别人的通知书"和"漏了一个人"。**

## 6. 期望覆盖的能力

- **Excel**：`open_workbook` → `get_sheet_list`（含隐藏表）→ `read_range` / `get_range_data` → 清洗列（空格、异体字、文本金额）→
  `remove_duplicates`（**判据是"该不该用"**：同名不同人时用它是错的）→ `save_as`（导出 CSV 数据源）
- **Word**：`open_document`（母版）→ `get_document_text` / `get_paragraphs` / `get_tables`（定位三处占位符）→
  **`wps_word_mail_merge`**（CSV → 新文档，母版不动）→ `save_as`（合订版）→
  逐份 `create_document` / `find_replace` / `set_table_cell` / `save_as`（每人一份）
- **转换**：`wps_convert_to_pdf`（24 次，**必须点明 `appType: word`**，见陷阱 11）
- **通用/收尾**：`wps_common_save_as`、`wps_word_get_open_documents`、`wps_excel_get_open_workbooks`、
  `wps_status`、`wps_batch`（批量连续调用）、`wps_call`（非广告面工具）
- **第三方库**（模型可能选）：python-docx / openpyxl 直写 —— **允许**（S4 的模型就这么干过），但判据只看产物

## 7. 验证器陷阱（预告，写验证器时就要堵住）

> S1 抓出 7 处、S2 抓出 7 处、S3 抓出 2 处（其中一次是**对模型的假指控**）、S4 抓出 2 处验证器自身缺陷。
> 本场景的 11 条陷阱在写核验器时先堵住，并如实标注哪些是**实测确认**、哪些是**预判**。

| # | 陷阱 | 对策 |
| --- | --- | --- |
| 1 | 姓名里的空格与全角空格：`李 娜` 与 `李娜` 是**同一人**，但 `王磊`/`王 磊` 在本 fixture 里是**两个人**（工号不同） | 判定一律以**工号**为主键；姓名只做"是否出现"的辅助判；规范化只用于**匹配文件名**，不用于合并身份 |
| 2 | 异体字/生僻字：`曽`↔`曾`、`堃` 的编码 | 先做 Unicode NFC 归一；归一后仍不同的，按 `expected.json` 的映射表比；表外一律判红 |
| 3 | `张雨涵` / `张雨含` 字形相近 | **绝不做模糊匹配**；只按工号认人（否则会把两个真人的文件判成一份） |
| 4 | 部门里的全角括号 / 顿号进文件名 | 判定时**只比规范化后的主体**（去掉 Windows 非法字符、统一全角→半角），不硬编一个"标准文件名" |
| 5 | 表尾 `合计` 行与空行 | 名单解析按"工号列匹配 `NC\d{7}`"过滤，不按行号硬编（除非与 fixture 逐行核对） |
| 6 | 隐藏工作表 `_tmp` | 校验时用 `workbook.sheetnames` 明确列出，判"没把 `_tmp` 当数据源" |

## 12. 走查中查出的插件缺陷（P0，已修）

### 12.1 现象（裸 COM 探针，可重跑）

`wps_word_mail_merge` 在**修复前**的行为，用 `tools/probe-mailmerge3.ps1` 逐条读数：

| 观测 | 读数 | 证据 |
| --- | --- | --- |
| `Fields.Add` 之后母版正文变成什么 | **正文被字段码顶掉**：`人事通知书_模板.docx` 的正文只剩 `«Dept»`（7 字符），模板原文全部丢失 | probe3 第 11 行 |
| 占位符是否被替换 | **从不**。合并结果里 `⟨姓名⟩`…`⟨生效日期⟩` 原样保留 | probe3 第 22 行读到的 3 份记录里 `工号：⟨工号⟩` 仍是占位符 |
| 数据落在哪 | 字段值被塞在**上一条记录的末尾**（`2026年10月12日` 之后紧跟 `制造中心（一车间）王磊`），不是占位符处 | probe1 的真实产出 `probe-out/probe-merged.docx` 第 9 段 |
| 记录数 | 3 条数据产出 **4 份**内容（多一份空模板）；`FirstRecord/LastRecord=1..1` 拿到的是**空**记录 | probe4 第 3–7 行 |
| 工具自述 | **回 success**（"已按数据源合并到一个新文档（原文档未改动）"），只有一条"2 个打开的文档"的 warning | probe1 的 `p3-mail-merge` |

也就是说：**一个宣称"一次生成几十份文档、母版不动"的功能，实际既没有替换数据，也破坏了母版正文，
还回了成功** —— 正是本项目 R11 要消灭的那种「假成功」，而唯一的测试
（`test/word-longtail.test.mjs:66-67`）只断言"产生了新文档"，所以它一直没被发现。

### 12.2 根因

1. 字段被 `MailMerge.Fields.Add($target, …)` 插到 `Get-MainTextRange` 给出的**当前选区**，
   而不是模板里写占位符的位置；WPS 对折叠选区的处理还会把正在插入的位置上的正文整段替换掉；
2. WPS 的 `MailMerge.Execute()` 并不把 `Fields.Add` 之后的字段当成"模板里的合并域"来替换 ——
   它产出的新文档里字段值按记录顺序堆在正文末尾，占位符原样保留；
3. 因此整条链路没有一处**校验产出**：`Execute()` 不抛错就当成功回报。

### 12.3 修法（已落地）

把「字段插到选区 + Execute」换成**按占位符做替换 + 逐行渲染**（`mcp/scripts/wps-com.ps1` 的 `mailMerge` case）：

- 数据源由桥自己按 RFC4180-lite 读（UTF-8 / 容 BOM / 支持引号），不再依赖 Word 的 `DataSource`；
- 字段 → 占位符按**名字**匹配（`⟨字段名⟩`、`{{字段名}}`、`«字段名»`，并对 `Name/Dept` 保留常见中文译名兜底），
  用 `Find/Replace` 落到占位符处 —— 不猜、不追加到末尾；
- 新增 `splitDir`（+ `fileNameField`）：**每个数据行一份 docx 直接存盘**，这是"一次生成几十份文档"的真实用法；
- 新增 `outputPath`：单文档模式把合订版存到指定路径，不再只回一个未存盘的内存文档名；
- 找不到占位符 / 有字段替换失败 → 走 `Add-WpsWarning`（R11：shortfall 会把 `success` 翻成 `false`），
  不再静默产出"看起来成功、其实没有数据"的文档。

### 12.5 真机第 1 轮又抓到第二个缺陷：`fileNameField` 指向的列被无视（已修）

第 1 轮（attempt 1）**24 项硬判据全过**，但模型的回答里主动报了一条工具行为：

> `wps_word_mail_merge` 的 `splitDir` 生效了（确实一行一份），但 `fileNameField` 没起作用，
> 生成的是 `row1.docx…row24.docx`；我按你给的第二种办法，用 CSV 里的「文件名」列自己改名。

它传的是 `fileNameField: "文件名"`——一个**只用于命名、不参与替换**的列（拼好的 `通知书_部门_姓名_工号`）。
桥路径复现（`run/bridge-out-named/`）确认：文件确实全叫 `row1.docx…row24.docx`。

**根因**：`$values` 是按 **`fields`** 建的，不是按 CSV 表头建的；`fileNameField` 指的列只要不在 `fields` 里，
查表就永远取到空串，于是回落到 `rowN` 兜底。诊断输出（当时的临时 warning）：

```
S5DIAG  fileNameField=[文件名] nameField=[文件名] header=[姓名|工号|部门|岗位|基数|生效日期|文件名]
        colKeys=[生效日期|岗位|文件名|部门|工号|基数|姓名] hasKey=True
S5DIAG2 r0 label=[] vkeys=[生效日期|岗位|部门|工号|基数|姓名] val=[]      ← 文件名 不在 $values 里
```

**修法**：`$rowValue` 改为按**表头**建全列映射（不是 `$fields`），单文档模式同样走它；
并且 `fileNameField` 顺带支持**带 `{列名}` 的模板**（`通知书_{部门}_{姓名}_{工号}`），数据源没有预拼列时也能一次到位。

**修复后验收**：

| 形式 | 结果 |
| --- | --- |
| `fileNameField: "工号"`（列名） | `NC2026101.docx…NC2026125.docx` ✅ |
| `fileNameField: "文件名"`（列名，列不在 fields 里） | `通知书_制造中心（一车间）_王磊_NC2026101.docx` ✅ |
| `fileNameField: "通知书_{部门}_{姓名}_{工号}"`（模板） | 同上 ✅ |

第 2 轮（attempt 2，prompt 里给了模板写法）**一次到位**，模型没有再改名，也没有再报这条。
