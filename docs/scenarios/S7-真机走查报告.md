## 4. 发现

### 4.1 D1｜能力缺口（P1，定性明确）：Word 分节族三件套在插件里做不了

| 缺口 | 源码/实测证据 | 影响 |
| --- | --- | --- |
| **分节页面设置** | 桥 `setPageSetup` 写 `$doc.PageSetup`（`host/wps-actions.ps1:6077-6082`），**没有 `section` 参数**；而同族 `getPageSetup` 有 `section`、按节读（`:6049-6057`） | 多节混合纸张/方向**完全做不到**；且改变方向会把边距整体旋转（本次实测 `left 56.7 / top 85.1`） |
| **页码格式与重新编号** | `insertPageNumbers` 参数只有 `alignment/includeTotal/position/section/showFirstPage`（`:1553`）；全表 270 个 action 无 `NumberStyle` / `RestartNumbering` / `LinkToPrevious` | 罗马数字、分节重开、续前节**都做不到** |
| **表头跨页重复** | `setTableFormat` 只有 `style/borders/autoFit/headerShading`（`:7729`） | `Row.HeadingFormat` 无处可设 |

> 这三条都是**"缺能力"而不是"实现错"**：调用时插件**如实报错**（`未知参数` / `unknown parameter`），
> 没有出现"回 success 但文件没变"的假成功。按 R11 口径，这属于**已知能力边界**，
> 需要在 README「现在还做不到的」里如实登记，或者补工具（见 §6 D3）。

### 4.2 D2｜参数面不一致（P2，新发现）：`paperSize` 在广告面缺失

实测同一件事两条路读到的参数白名单不一样：

- `wps_word_set_page_setup({paperSize:"A3"})` → `未知参数: paperSize ... 可选参数: orientation / topMargin / bottomMargin / leftMargin / rightMargin`
- 但桥的 `setPageSetup` **是接受 `paperSize` 的**（桥参数表 `'setPageSetup' = @('bottomMargin','leftMargin','orientation','paperSize','rightMargin','topMargin')`），
  而且 `wps_execute_method(setPageSetup, {paperSize:A3})` 那条**确实成功改成了 A3**。

即：**桥有、工具的 MCP schema 里没有** —— 用户按 `wps_help` 学到的是"不能设纸张大小"，实际上应用层能做。
这与 WO-001 记过的"读写不对称"是同一族问题（参数面与桥对不上），**建议补进 `wps_word_set_page_setup` 的 schema**。

### 4.3 D3｜`wps_execute_method` 的边界（记录，不是缺陷）

逃生舱**过参数白名单**（`unknown parameter(s) for 'setPageSetup': probekey`），
但**不做参数名友好映射**（`paperSize` 能过、`probekey` 不能过）。模型用两次探测就摸清了边界，没有硬耗。

### 4.4 无假成功（R11 核心不变量）

逐条核对 160 次调用与产物：**没有任何"回 success 但文件里找不到对应事实"的步骤**。
唯一一次"看起来失败"的 `wps_word_close_document` 是模型自己 `job_kill` 了后台任务之后的重试，属正常收尾。
第 13 条要求（关文档 + 列还开着的文档）实测 `当前没有打开任何文档`。

### 4.5 模型方的三个判断（记录，供产品口径参考）

1. 删掉了初稿里两段**写给编辑看的说明文字**（"上面那处引用是原稿里直接敲的方括号…"），并说明了理由；
2. 正文格式（宋体/小四/1.5 倍/首行缩进）**只施加在叙述段**，排除标题/表格/封面/目录；
3. 第 3 节上下边距按第 1 节取 2cm（prompt 只点名了左右 3cm）。

三条都在答复里显式说明并给出"不对就说，初稿还在"的退路 —— 这是本项目想要的**诚实行为**，不是缺陷。

## 5. 核验器自身缺陷（4 处，都已修；其中 2 处差点变成对模型的假指控）

> S1 抓出 7 处、S2 抓出 7 处、S3 抓出 2 处、S4 抓出 2 处、S6 抓出 1 处。本轮 **4 处**。

| # | 缺陷 | 后果 | 处置 |
| --- | --- | --- | --- |
| 1 | `w:pgSz/@w:w` / `w:pgMar` 的**单位**：官方是 twip，但 WPS 写出来可能是 **EMU**，而且**同一份文档不同节可以混用**（实测：第1/2节 EMU、第3/4节 twip，A3 那节甚至是 `w=23814 twip / h=16839 EMU` 的混合写法） | 首判把 A4 读成"11906×16838 磅"、把边距读成"1701 磅"→ **B3/B4 假红** | 改成**按节**用"纸张长边必须落在 400–1700pt"两假设分类（`_section_unit`），统一口径后再算 |
| 2 | 域代码匹配写成 `"PAGE" in hf["fields"]`（列表**精确元素**匹配），而实际元素是整条指令 `'PAGE \* roman \* MERGEFORMAT'` | **C1/C3/C4 假红**（模型明明做了） | 改成逐条 `\bPAGE\b` 词匹配（`has_code`） |
| 3 | 罗马数字只认"节属性 `w:pgNumType/@w:fmt`"一条路 | 模型走的是**域开关 `\* roman`**，会被误判 | `roman_ok()` **两条路都认**，并在 detail 里写明走的哪条 |
| 4 | 我自己造的 known-good 把**磅当 twip**写进 `w:pgSz`（595 而不是 11906），成了"邮票纸张"；而核验器当时也在瞎猜单位，**两边一起错反而全绿** | 基准产物不可信 | `make_sect_pr` 改成入参磅、写出 twip（×20），重建 known-good + 25 个 broken 集 |

**修完后的回归**：`known-good` 硬 **30/30**、软 5/6（缺 PDF 那项按设计不给）；**25 个单缺陷 broken 集全部在预期判据上变红**（`selfcheck.py` exit 0）。
即：**核验器既认得出对，也认得出这 30 类错。**

### 6.3 本次走的弯路（留给下一轮省时间）

- **实时看 stdout 是空的，但最终答复确实在 stdout 里**：这个 one-shot CLI 把**过程**（reasoning / 工具往返）
  写到 **stderr**，把**模型最终答复**写到 **stdout** —— 但 stdout 直到进程退出才落盘
  （运行中 `s7a.stdout.txt` 一直是 0 字节，跑完是 6,303 字节的完整中文答复）。
  **要工具级轨迹就得读会话 JSONL**：`%DSH_HOME%\sessions\--<cwd>--\<session>\session.v4.jsonl.zstd`
  （774 条记录：109 step、160 tool/call、160 tool/result）。
- **会话日志是多帧 zstd**：Node 的 `zstdDecompressSync` 只解第一帧（本次第一帧只有 165 字节的 session 头），
  必须按 magic `28 B5 2F FD` 逐帧解 —— `zstd-multiframe.mjs` 干这个（493 帧 / 3.26 MB / 0 失败），
  再由 `tool-trace-s7.mjs` 抽 `tool/call` 与 `tool/result`。
- **`extract-trace-s7.mjs` 是照 `.stdout.txt` 当 JSONL 写的，本次没用上**（stdout 是 markdown）。
  下一轮直接用 `zstd-multiframe.mjs` + `tool-trace-s7.mjs`；`.stdout.txt` 用来看最终答复即可。
- 真机耗时 **约 25 分钟**（16:29:24 → 16:54:41），比 S5/S6 长得多：模型花了大量步骤在**探测能力边界**上
  （两次逃生舱失败、多次全节回读、写 17 KB 的 COM 转换脚本、自写 PDF 文本核对脚本）。
  这本身是**有价值的读数**：当插件缺能力时，模型会用"读源码 + 打探针"把它钉死，而不是硬猜。

### 9.4 附带修掉的两个同源缺陷（本轮跑门禁时暴露）

**① 测试装置的 MCP 收帧把中文读坏**（`test/lib/harness.mjs` + `test/spec-reproduction.test.mjs`）。

`spec-reproduction` 一度报 2 红：`wps_ppt_set_background_image` / `wps_excel_set_outline_levels` 的描述与活面对不上，
活面那侧带 U+FFFD。**看起来像产品坏了，实际是读法坏了**：

| 实验 | 结果 |
| --- | --- |
| 子进程自己把描述**写文件** | `fffd=0` |
| 同一份 `mcp/dist` 走 MCP stdio 管道 | `fffd=2 / 3` |
| 抓服务器 stdout **原始字节** | `efbfbd` 出现 **0 次**（线上是干净的） |
| 字符串式缓冲 `buf += d.toString('utf8')` vs 字节式分帧 | 字符串式坏、字节式干净 |

**根因**：`d.toString('utf8')` 按 chunk 解码，多字节 UTF-8 被切在两个 data 事件之间就成 U+FFFD。
已把两处改成**按字节收帧**；冻结判据仍是逐字节严格比对（中途那版"白名单折叠"补丁已撤）。
`spec-reproduction` 随即 **16/16 绿**。这条对 S7 的意义：**判据本身的读数也可能是"装置缺陷"**，
与 §5 里那 4 处核验器缺陷是同一类教训。

**② `mcp/src/spec/operations.ts` 里 3 个历史坏字符**：`把<U+FFFD><U+FFFD><U+FFFD>细` → `把明细`（按码点修）。
