> 依据：改进指南 §10.2 / §10.3 / §10.4。
> 本文件固定**输入、初始文件、用户提示与成功标准**，让「新旧 Skill 谁更好」可以重复测量。
> **状态说明（不要误读）**：本文件里的场景标准已经固定下来；本轮**没有跑模型侧对比**
> （本环境没有可用的 DSH 交互会话，也没有跑三轮以上的预算）。因此下面每一行都明确标了
> 「已有确定性证据」还是「仅固定标准，待跑」。**"写了测试用例"不等于"场景已经通过"。**

## 1. 场景集

初始文件一律用**专用临时文档**（`test/.artifacts/<scenario>/`），不拿用户正在编辑的文件做破坏性测试。
"确定性证据"一列指的是**不依赖模型**、可重复执行的检查（裸 COM / 外部解析 / 工具返回值）。

> **就绪状态**：15 个场景里 **12 个已在 [test/skilleval/](../test/skilleval/README.md) 里可跑**
> （有夹具 + 确定性断言），模型侧结果见 §4。剩下 3 个（#2 不是任务场景、#12 缺超时注入开关、
> #14 缺确定性 shortfall 触发点）在 README 里写明了原因，**不计入已跑**。
> 最后一列只是"这个场景在模型侧跑没跑过"的状态；数值结果在 §4。

## 2. 比较方法（§10.3）

> 可执行的场景表、夹具生成、提示词与**确定性断言**已落到 [test/skilleval/](../test/skilleval/README.md)：
> `node test/skilleval/run.mjs --dry-run` 生成输入夹具与断言清单（不调模型、不需要 WPS），
> `node test/skilleval/verify.mjs <场景key>` 对产物做判定（正例/反例都已验证过会 PASS/FAIL）。
> §1 的 15 条与 `test/skilleval/scenarios.mjs` 一一对应：**12 条可跑**，3 条写明未做原因。

对同一场景、新旧 Skill 各跑一轮，**必须固定**：模型、Harness 版本、工具档位（`WPS_OFFICE_STANDARD` = standard）、
初始文件（同一份 fixture）、温度等采样参数。

每轮记录：

| 指标 | 怎么量 |
|---|---|
| 任务最终成功率 | 按上表的"成功标准"逐项判定；不看模型自述 |
| 错误目标次数 | 非目标文件出现的写入次数（用独立解析/裸 COM 对比基线指纹） |
| 数据丢失次数 | 目标文件内容缺失或原稿被改的次数 |
| 无依据成功声明次数 | 模型声称完成但确定性检查为否的次数 |
| 工具调用总数 / 无效调用数 / `wps_help` 查询数 | 从会话 JSONL 统计 |
| Skill / reference 实际加载量、tokens | 按 Harness 的实际计费/加载读数，**不用字符数估算** |
| 执行耗时、重复询问次数、恢复成功情况 | 会话时间线 |

代表性场景**至少重复三轮**，报告波动区间；优先选成功率和正确性更好的方案，而不是"一轮调用最少"的方案。

> 记录模板：
> ```
> 场景# / 轮次 / 模型 / Harness / 档位 / skill 版本(commit) / fixture 哈希
> 结果：成功 | 部分 | 失败    证据：<文件 + 断言>
> 调用数=…  无效=…  help=…  加载 tokens=…  耗时=…  重复询问=…  恢复=…
> ```

## 3. 验收状态（哪些已验、哪些还没验）

1. **Harness 侧的 Skill 加载与相对路径读取 —— 已实测（2026-10-17，`wpse2e` profile，headless 会话）。**
   结论：① 只加载应用 Skill 时**不会**自动带出总 Skill（返回里只有一句指针）；② 相对 `references/`、
   `recipes/` **能读到**，base directory 明确交付给模型；③ 读不到文件的错误是
   `Error: cannot read "<绝对路径>": not found`；④ 能按路径读另一个已注册 Skill 的文件；
   ⑤ 顺着应用 Skill 的指针加载 `wps-office-next` 成功，正文含「保存、副本与关闭」「没有 documentId」。
   详细证据与原始返回见 [skill-audit.md](skill-audit.md) §4.1。因此四个 SKILL.md 保留关键协议短摘要的
   降级设计**被证实是必要的**；细节放 `references/` `recipes/` **被证实是安全的**。
2. **视觉验收 —— 未做**：文字溢出、对象重叠、裁切需要导出图片 + 图像读取能力；Skill 里写的是
   "读不到图片就说视觉效果未验证"，不是"排版无误"。
3. **模型侧对比（新旧 Skill）—— 已跑三轮（2026-10-17/18，见 §4）**：6 → 12 → 14 个场景，两臂各 3 轮。
   最终在**共享的 12 个场景**上：两臂都是 **35/36**（唯一失败是 hidden-tool 第 1 轮被 60s 上限截断），
   新臂平均 tokens ≈ 503k/轮 vs 旧臂 495k/轮（**+2%**，已从最初的 +8% 收敛），墙钟时间 +5s/轮。
   另有两个只能在新臂测的故障场景（#12 写入后超时、#14 部分未生效）：**6/6 通过**。
   **不能**外推成"模型更容易选对工具"：样本小、单模型、每场景 3 轮、轮间方差很大（见 §4.3）。
4. **危险/异常场景**（超时、部分生效）—— **已做**（2026-10-18）：加了默认惰性的受控故障注入
   （`WPS_OFFICE_FAULT_INJECT`，见 [test/skilleval/README.md](../test/skilleval/README.md)），
   #12/#14 各 3 轮全绿。契约层仍由 `test/watchdog.test.mjs` / `test/honest-reporting.test.mjs` 钉住。

## 4. D1 实测结果（2026-10-17，两轮）

**设置**：同一模型（deepseek-flash）、同一 Harness、同一 `WPS_OFFICE_TOOLSET=standard`、同一夹具与提示词；
两臂只换插件代码。新臂 = `wpse2e`（junction → 工作区，代码含本轮全部改动）；
旧臂 = `wpse2e-old`（git worktree 固定在重构前提交 `bc69b96`，独立 profile，串行跑）。

### 4.3 第三轮：两个故障注入场景（只有新臂能跑）

| 场景 | 轮次 | 通过 | 平均 tokens/轮 | 平均耗时 | 说明 |
|---|---|---|---|---|---|
| write-timeout（#12） | 3 | **3/3** | 420,103 | 33s | 第一次 `insert_text` 执行后回「状态未知」；三次都先读回、确认只追加一次 |

- #14 是**已知慢场景**：持续 shortfall 让模型反复排查，实测 86–113s、29–45 次工具调用、平均 1.5M tokens。
  它没有追求"快"，而是验证"不谎报成功"——三次回答都如实列出未生效项，没有一次声称已改。
- 旧代码跑这两个场景没有意义：没有注入时它们退化成普通写入/格式化任务。

### 4.4 读这些数字时必须知道的事

1. **第一轮不是最终结果，三次修法都是改接口、不是加说明**：
   - keep-original 首跑新臂 1/3 失败：副本存到不存在的 `output/` → `save_as` 只回「文档保存失败」→
     模型建目录重存后**声称成功但副本没改**。给桥加输出目录前置检查后 3/3，平均 tokens 732k → 400k。
   - sections-mixed 首轮超时：只改方向时 WPS 把纸张代码从 7(A4) 变成 **41**，桥只回「纸张: 41」，
     模型当成缺陷反复排查。桥改成「41（横向纸张代码）」后 3/3、23–42s。
   - partial-failure 首轮：`wps_word_set_font` 的 `range` 只声明 object，而描述/桥都支持 `"all"` ——
     模型按描述传 `range:"all"` 被参数形状守卫拒绝。声明补成 `["object","string"]` 后正常。
   - 三次都印证 §11-D「优先改接口，再补必要说明」。
2. **测量被环境打断过，重跑过 8 轮**：WPS 在跑动中被手动关闭 / 超时残留进程占着 xlsx 锁 / 一次误删
   `result.json`（已用 `--rebuild-missing` 从会话日志重建，重建记录不带 `timedOut`）。被替换的旧结果不计入。
3. **轮间方差很大**：同一场景 3 轮的 tokens 相差 2–3 倍（two-word-target 早期一轮 944k、后期 271k），
   所以"某场景贵/便宜"的单点差异不能当结论，只能看整臂均值与大方向。
4. **样本很小**：每场景 3 轮、单模型单机，**没有统计显著性**。能说的只有方向：
   - 共享 12 场景正确率相同（各 35/36，失败的是同一场景的同一类 60s 截断）；
   - 新臂在 8 个场景更省 token、4 个更贵，整臂均值 +2%；
   - 两个故障场景新臂 6/6 如实处理（旧代码无法对照）。
